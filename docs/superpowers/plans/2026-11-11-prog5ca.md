# PROG-5C-A Implementation Plan

**Goal:** bounded versioned pending consent requests, inspection, revocation and pure eligibility; no execution or human acceptance invented.
**Architecture:** existing ProgressionModule/repository, new internal consent service, pure domain contracts/policy/evaluator, two relational aggregate/event tables, versioned JSON snapshot, UTC local READ COMMITTED fences and paired deferred SQL audit constraints.
**Spec:** PROG-5C-A attachment ad9568c5-daaf-46ae-baf6-5f5db0dc54d8.

## Decisions and alternatives

A boolean or reuse of manual 5A approval cannot express recurrent consent and is excluded. Extending applications/reviews would conflate authorization and execution, so additive dedicated consent/events is the smallest cohesive design. Only PENDING_CONFIRMATION/REVOKED stored. No ACTIVE transition, executor or acceptance method. Expiry is logical. Exercise required; plan optional means exact enumerated destinations only. Selector never chooses a destination: EXACT_PRESCRIPTION_ALLOWLIST. Configuration changes stay pending and generate a new immutable version/event. Decision-relevant settings and exact policy are bound; informational updatedAt/autoApplyAuthorized do not grant or widen permission.
